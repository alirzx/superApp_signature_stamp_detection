# Local and server deployment

1. Local builds are **not** part of the rollout. Create a local `.env` only to inspect config; the team will later build exclusively on the server via GitLab CI. Copy `.env.production.example` on the deployment host or inject its full contents via a protected GitLab File-type variable. Never commit the real `.env`. Replace the API token with `openssl rand -hex 32`; keep `.env` out of Git. Set API port 8006 and UI port 8087, provided they are available on the host.
2. The other SuperApp services use an approved LAN interface `192.168.4.209`; production template binds `UI_BIND_IP` to that address, while `API_BIND_IP=127.0.0.1`. **Confirm that interface and network route before deployment.** Remote clients on the same permitted LAN/VPN can open `http://192.168.4.209:8087` if the firewall allows it. Avoid public exposure without authenticated HTTPS ingress.
3. After the team verifies the existing GitLab CI and its server branch checkout, deploy on the server. `docker compose up --build -d` builds images, runs the one-shot model-setup before API, and starts the independent static UI. Keep `model_cache` (do **not** use `docker compose down -v`). The frontend can start while model initialization is unavailable and displays a backend-offline message.
4. Check `docker compose ps -a`, then `docker compose logs --tail=150 model-setup api ui`, `curl -f http://127.0.0.1:8006/health/ready`, and `curl -f http://192.168.4.209:8087/healthz` from an allowed host (replace the IP if changed).
5. Run a **real sample** through `/v1/detect`, validate overlays and JSON coordinates, test file limits, then record RSS and p50/p95 latency. API budget `4g`/`2.0` cores is only a provisional starting point.

## Build supply chains

Backend uses `python:3.11-slim-bookworm` with Liara as primary and Chabokan as fallback for normal Python packages. CPU-specific Torch (`2.14.0+cpu`) and torchvision (`0.29.0+cpu`) are installed via the official CPU wheel index with `--no-deps`; their ordinary dependencies are first installed from the regional mirrors. A final `pip check` plus `torch.version.cuda is None` assert is mandatory. Frontend npm uses Liara as the primary registry with a configurable official npm fallback; if both are blocked, supply a reachable internal registry. Nginx gettext uses the Liara Alpine mirror first, then the Huawei Cloud Alpine mirror. CPU API system packages use signed Debian Bookworm repositories with primary/fallback HTTPS mirrors. PyTorch and Hugging Face downloads are independent of the PyPI mirrors. Hugging Face weights, Docker Hub images and the PyTorch binary wheel come from their own distinct sources; Python mirrors do not cover them.

The team-owned `.gitlab-ci.yml` **is present** and is deliberately left unchanged. It triggers on GitLab `master`, copies `ENV_FILE` to the server and runs `docker compose up --build -d`. The current script still executes `git pull origin main` on the server, unlike the Time-Series `master` deployment (`git pull origin master`); this is an **unresolved CI blocker** if the server repository does not have a correctly maintained `origin/main`. Ask the CI owner to correct the pull branch before the first rollout. The established server directory in the actual CI is `/opt/apps/ai-service/signature_stamp_detection`, not the old `_module` suggestion. The CI presently does not enforce a model-readiness smoke gate, and its `ssh-keyscan` step needs independently verified host-key handling during a later CI review. Do not infer successful deployment merely from Docker Compose returning zero.

## CI teammate handoff (server-only build)

The organization branch is **`master`**, not `main`. Actual CI server path: `/opt/apps/ai-service/signature_stamp_detection`. Current CI variables are `SSH_PRIVATE_KEY`, `SSH_USER`, `SSH_PORT`, `VM_IPADDRESS` and `ENV_FILE`. `SSH_PRIVATE_KEY` is consumed as inline secret text by `ssh-add -`; `ENV_FILE` must be a readable file path supplied by a GitLab File-type CI variable. Store the complete production `.env` in a protected File-type variable named `ENV_FILE` (unless the CI owner updates the code); for File-type variables the variable value exposed to the job is a *path to the temporary file*, so copy it into the server deploy directory securely (0600), never echo it in logs. Protect the deploy branch, use SSH key + pinned known_hosts, and fail before Compose when required variables are missing. The target host must have the configured LAN address (or override `UI_BIND_IP`), open only UI port 8087 to approved clients, and keep API 8006 loopback-only. Keep model downloads and image builds on the server, never on the developer laptop. Do not enable automatic rollout before a real stamp/signature CPU smoke test succeeds.

**Release checks before enabling CI:** Confirm (a) the server checkout exists at `/opt/apps/ai-service/signature_stamp_detection`; (b) its Git remote has the expected branch; (c) the runner has working SSH/scp and correct credentials; (d) the exact `ENV_FILE` secret is installed without exposing the token in logs; (e) the server owns `UI_BIND_IP`; (f) the server can reach the configured package mirrors, Docker base-image registry, PyTorch CPU-wheel index and Hugging Face for first bootstrap. Verify `docker compose --env-file .env config --quiet`, `model-setup` exit 0, `/health/ready`, `/healthz`, and at least one real model detection. The model setup is one-shot and mandatory before API via Compose; the UI runs independently. No local Docker build is needed.

Frontend package.json uses pinned direct versions but currently has no npm lockfile. First validated server build should generate and review a `package-lock.json` in a follow-up reproducibility commit; switch the build stage to `npm ci` at that point. Until then npm resolves transitive dependencies afresh at build time, so reproducibility is not guaranteed.

## Operational constraints

The model is retained on the `superapp-signature-stamp-detection_model_cache` named volume, mounted read-only by the API. The API uses a non-root user and a read-only root filesystem with bounded `/tmp` tmpfs. UI Nginx is non-root and runs on internal port 8080. `API_TOKEN` is only inside the server's environment and Nginx config, never in React's compiled JavaScript. **Nginx proxy token is not per-user auth.** Require trusted firewall/VPN and preferably an authenticated HTTPS ingress. Distinguish UI `/healthz` from API `/health/ready`.
